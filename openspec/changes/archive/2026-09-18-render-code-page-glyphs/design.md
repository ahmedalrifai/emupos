## Context

`glyphs.py` maps a printed byte to a character through the profile's code page, then draws that
character from a bitmap table generated by `scripts/generate_glyphs.py` from Spleen (BSD-2-Clause).
`GLYPH_CODE_PAGES` currently holds PC437 alone, so every other code page renders a placeholder box
per byte and emits `printer.codepage.unsupported`, while the text dump still shows the characters.

The shipped profiles claim 12 code pages between them:

| Profile | Code pages |
| --- | --- |
| `epson-tm-t20iii` | PC437, PC850, PC860, PC863, PC865, WPC1252, PC866, PC852, PC858, PC720, PC864, WPC1256 |
| `rongta-rp326` | PC437, PC864, PC720, WPC1256 |
| `xprinter-xp80t` | PC437, PC864 |

Measured against Spleen 2.2.0, the 575 code points those pages need break down as:

- 411 are in Spleen (Font A: `spleen-12x24`, or `spleen-16x32` downscaled; Font B: `spleen-8x16`).
- 164 are not, nearly all of them Arabic. Spleen has no Arabic block at all.

The X.Org misc-fixed fonts have all 164. `10x20.bdf` and `9x15.bdf` in `font-misc-misc-1.1.3` carry
5205 and 4777 glyphs, cover PC864 completely, and their `COPYING` reads "Public domain font. Share
and enjoy." Their cell sizes sit just under emupos's: Font A is 12x24, Font B is 9x17.

The other candidate, GNU Unifont, is 16x16; downscaling to 12x24 broke the strokes of Arabic letters
in a side-by-side test, and its licence (OFL / GPLv2+ with the font exception) is heavier than public
domain for no gain.

## Goals / Non-Goals

**Goals:**

- A glyph for every character of the 12 code pages the shipped profiles claim, in both fonts.
- Arabic that reads as joined words, on the same baseline as Latin text on the same line.
- Character placement that matches a real printer: one cell per byte, in the order received.
- A generator a maintainer can rerun to add a code page or update a font, from pinned sources.

**Non-Goals:**

- Right-to-left reordering or letter joining of the incoming bytes (D4).
- Matching a vendor's ROM typeface. The promise stays dot-accurate geometry, approximate shapes.
- Code pages no shipped profile claims (Greek, Hebrew, Thai, Kanji). Adding one later is one entry
  in the generator's list plus a regeneration, as long as a source font has the characters.

## Decisions

### D1. Two font sources, Spleen first and misc-fixed second

`generate_glyphs.py` downloads both archives, each pinned by version and SHA-256, and takes each
glyph from the first source that has it:

- Font A (12x24): `spleen-12x24`, else `spleen-16x32` downscaled (today's behaviour), else
  `10x20.bdf` from misc-fixed.
- Font B (9x17): `spleen-8x16`, else `9x15.bdf` from misc-fixed.

Spleen keeps priority so every glyph emupos already renders stays exactly as it is, and existing
golden images do not move. misc-fixed is added at
`https://www.x.org/releases/individual/font/font-misc-misc-1.1.3.tar.xz`
(SHA-256 `79abe361f58bb21ade9f565898e486300ce1cc621d5285bec26e14b6a8618fed`).

The generated tables grow from 251 to 575 glyphs per font, roughly 60 KB per file. The file header
names both fonts and carries both licence texts.

*Alternatives:* Unifont (strokes broke when downscaled to the Font A cell, heavier licence);
rasterising an outline font such as Noto Naskh Arabic (needs FreeType at generation time, output
varies with the rasteriser version, and the licence is OFL rather than public domain).

### D2. Baselines aligned by the two fonts' bounding boxes, not by eye

BDF records the cell and its baseline: Spleen 12x24 is `FONTBOUNDINGBOX 12 24 0 -5`, so its baseline
is 5 dots above the cell bottom, and misc-fixed 10x20 is `10 20 0 -4`. Placing a misc-fixed glyph so
the two baselines coincide gives a fixed offset per font, computed from the bounding boxes rather
than hard-coded:

```
 Font A cell 12 x 24                   Font B cell 9 x 17
 ┌────────────┐ row 0                  ┌─────────┐ row 0
 │ ▒▒▒▒▒▒▒▒▒▒ │ ← misc-fixed 10x20     │▒▒▒▒▒▒▒▒▒│ ← misc-fixed 9x15
 │ ▒▒▒▒▒▒▒▒▒▒ │   starts at row 3      │▒▒▒▒▒▒▒▒▒│   starts at row 0
 ├────────────┤ row 19 baseline        ├─────────┤ row 12 baseline
 └────────────┘ row 23                 └─────────┘ row 16
   ↑ 1 dot of padding each side          full cell width: joins already meet
```

Font B needs no horizontal padding: misc-fixed 9x15 is exactly as wide as the cell. Font A's
glyphs are 10 dots wide in a 12-dot cell, padded by 1 dot on each side, which D3 then fills for
joining letters.

### D3. Extend a joining letter's connecting stroke to the cell edge

Arabic letter forms connect through a stroke that runs to the edge of the glyph. With 1 dot of
padding on each side in Font A, the strokes of neighbouring letters would stop 2 dots short of each
other and words would print as loose letters.

Which side a form joins on is a property of the character, and the standard library knows it:
`unicodedata.decomposition('ﺒ')` is `'<medial> 0628'`. So:

| Form | Joins on the glyph's | Padding filled |
| --- | --- | --- |
| `<final>` | right | right |
| `<initial>` | left | left |
| `<medial>` | both | both |
| `<isolated>`, everything else | neither | none |

For a filled side, the generator copies the ink of the glyph's outermost column into the padding
columns on that side, which extends the connecting stroke (1 to 2 dots tall) without touching the
rest of the letter.

The rule is driven by the character's form, not by ink at the edge: in misc-fixed, 32 isolated forms
also touch a cell edge because wide letters fill the cell, and extending those would grow strokes
that should end.

In visual order the sides work out: a final form joins the letter that precedes it in reading order,
which sits to its right on paper, and an initial form joins the following letter, to its left.

Font B is unaffected — no padding, so joins already meet.

### D4. No right-to-left placement: the printer does not do it either

ESC/POS printers print each received byte into the next cell, left to right. They do not reorder
text and do not join letters; the POS does both before sending, which is why 72 of PC864's 122
characters are already-joined letter forms. Evidence:

- ReceiptPrinterEncoder #26, from its author: "The problem with ESC/POS printers is that they are
  pretty dumb ... Things like right-to-left support and glyph shaping is simply not supported."
- escpos-php #6 built an `RTLBuffer` in the driver, reversing the chunks itself, and closed with
  the conclusion that native ESC/POS Arabic is not feasible in the driver.
- A report against `react-native-bluetooth-escpos-printer` tested Xprinter, Epson, TSC and Bixolon:
  all printed Arabic reversed until the application reversed the string.
- qzind/tray #339 shapes and reorders with ICU before encoding to IBM-864.

So emupos renders bytes in the order it receives them, for every code page. This is not a
simplification: a POS that forgets to shape and reverse its Arabic gets a receipt image that looks
exactly as wrong as the paper one would, which is the point of a simulator. The text dump is
unchanged for the same reason — it holds the characters the bytes name, in the order they arrived.

Some Epson models (TM-T88VI and later) have an optional "Arabization" firmware setting, off by
default and switched on with an Epson utility; qzind found it garbled their output. If someone needs
it, it belongs in a later change as a profile field, not here.

*Alternative rejected:* applying the bidi algorithm when the code page is Arabic. It would make
emupos disagree with the printer it simulates and hide the most common Arabic POS bug.

### D5. The event now means "this printer has no such code page"

`GLYPH_CODE_PAGES` lists the 12 code pages. Two behaviours follow:

- `printer.codepage.unsupported` fires when the number is missing from the profile's map (for
  example Epson's 37 sent to a `rongta-rp326` profile), or when a profile names a code page emupos
  has no table for — profiles are user-editable, so this stays reachable.
- A byte with no glyph inside a code page that *does* have a table prints the placeholder for that
  one cell and emits nothing. This covers the bytes a code page leaves undefined (6 in PC864, 5 in
  WPC1252) and the characters neither font has:

  | Font | Missing | Which |
  | --- | --- | --- |
  | A | 12 | 8 bytes PC720 maps to C1 controls; U+200C–U+200F (zero-width and direction marks) |
  | B | 18 | the same 8 C1 bytes; U+200E and U+200F; 8 Urdu letters of WPC1256 (U+0679, U+0688, U+0691, U+0698, U+06BA, U+06BE, U+06C1, U+06D2) |

  A placeholder for a zero-width or control character is honest: emupos shows that the printer
  received a byte it has no shape for, rather than silently printing nothing.

No new event type and no new profile field, so the API and configuration are untouched.

### D6. Generator changes beyond the new source

- `needed_code_points()` currently decodes strictly and would raise on the first undefined byte;
  it must skip them (`UnicodeDecodeError`), as PC864 and WPC1252 both have them.
- `CODE_PAGES` becomes the 12 Python codec names. `GLYPH_CODE_PAGES` in `glyphs.py` lists the same
  pages under their profile names; a test keeps the two in step (D7).
- `parse_bdf` reads misc-fixed as it is: both fonts give a per-glyph bounding box, which it already
  places into the cell. Parsing `10x20.bdf` and `9x15.bdf` with it was checked while exploring.

### D7. Tests

- `test_render.py`: PC864 on the Epson profile renders glyphs and emits no event; a line of mixed
  Latin and Arabic keeps one cell per byte in the order received; a byte with no glyph prints a
  placeholder without an event; a number missing from the map still emits the event (unchanged).
- A table test over `GLYPH_CODE_PAGES`: for each page, every byte that decodes has a glyph in both
  font tables, except a small list of known gaps (D5). This fails when a code page is added to the
  constant without regenerating the tables.
- Golden cases: one case per code page printing its bytes `80`–`ff`, one with mixed Latin and
  Arabic, and the existing `code-page-placeholder` case reworked onto a number missing from the
  profile's map, so the placeholder path stays covered.

## Risks / Trade-offs

- **[Latin and Arabic come from different typefaces on the same line]** → Both are single-dot-stroke
  bitmap fonts of nearly the same size, and D2 puts them on one baseline. The mixed golden case
  makes any mismatch visible in review.
- **[The joining extension draws a stroke the real font would not]** → It only fills padding on the
  side the character's form declares it joins, and only with ink already at that edge. The per-page
  golden cases show every Arabic form.
- **[misc-fixed glyphs are 10x20 in a 12x24 cell, so Font A Arabic is slightly small]** → Accepted:
  geometry stays exact because the cell is what advances, and scaling 10x20 up would blur strokes
  the way Unifont did.
- **[Users read glyphs as a promise of ROM-identical output]** → The README limits row and the spec
  keep saying shapes are approximate; only the sentence about which code pages have glyphs changes.
- **[Someone expects emupos to lay Arabic out right to left]** → Documented in three places (README
  limits row, `docs/protocols/escpos-status.md`, the spec) as a deliberate match to real printers,
  naming the POS as the place to shape and reverse.

## Migration Plan

1. Update the generator, run `uv run scripts/generate_glyphs.py`, commit the regenerated tables.
2. Regenerate the golden cases with `EMUPOS_UPDATE_CASES=1` and review the diff: only cases that
   used a non-PC437 code page should change, because Spleen keeps priority for existing glyphs.
3. No runtime migration: no stored data, no configuration and no API surface is involved. Rolling
   back is reverting the commit.

## Open Questions

- Should Font B fall back to a squeezed 10x20 for the 8 Urdu letters it lacks, rather than printing
  a placeholder? Left as a placeholder for now; WPC1256 Urdu in Font B is a narrow case.
- Epson's "Arabization" memory switch as a profile field: out of scope here, worth an issue if a
  user has a printer configured that way.
